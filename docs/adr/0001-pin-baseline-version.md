# ADR-0001：把分析基线锁定在 Volcano v1.15.3

- **状态**：已接受
- **日期**：2026-10-05
- **决策人**：（填名字）
- **参与讨论**：全组
- **影响范围**：所有人 —— 环境、报告里的版本声明、实验可比性

## 背景

课程要求每个人独立输出一份分析测试报告，最后由组长汇总成一份总报告。
这意味着**至少 5 份报告的数据会被放在同一张表里横向比较**。

2026-10-05 时上游 `volcano-sh/volcano` 的 `master` 停在 `v1.16.0-alpha.2-24-gbbf87708f`，
即 1.16 的 alpha 线上。如果每个人按自己的节奏 `git pull`，会出现：

- 张三 10 月测的模块，李四 11 月测时已经被重构；
- 「我复现不了你的结果」变成常态；
- 汇总报告里的对比表在方法学上站不住脚 —— 三组数据的代码版本不同，差异可能来自上游改动而不是待验证的假设。

同时 `master` 处于 alpha 线，随时可能引入不兼容改动。

## 决策

**全组统一以 tag `v1.15.3`（commit `d2dd7024f4af3070f9d99d68a78973893908a743`）为唯一分析基线。**

- 该 commit 是当时最新的**正式 release**（非 pre-release），发布于 2026-09-30。
- 每份实验记录必须贴 `git rev-parse HEAD` 的输出作为复现锚点。
- 基线值集中记录在仓库根目录 `baseline.md`。
- 代码实验（打补丁、跑 e2e）从各自的 fork 分支进行，但 **fork 的基线也必须是这个 commit**。

## 备选方案

| 方案 | 优点 | 缺点 | 为什么不选 |
| --- | --- | --- | --- |
| A. 钉 `v1.15.3`（选中） | 可复现；已是稳定版；兼容 K8s 1.23–1.35 | 比 master 少几个新特性 | — |
| B. 钉 `master` / `bbf87708f` | 自带最新特性（如 unschedulable job cache、hint 索引等） | alpha 线，随时变；他人无法长期复现 | 结论的保质期太短，答辩时可能已被上游改掉 |
| C. 不统一，各人自选 | 零协调成本 | 数据不可比，汇总报告失去意义 | 违背课程目标 |

## 理由

1. **可复现性优先于新鲜度**：本项目的产出是"分析与测试报告"，不是上游贡献。报告的价值建立在别人能重跑出同样结果上。
2. **v1.15.3 的兼容面足够宽**：上游 README 矩阵标注 Volcano v1.15 与 Kubernetes 1.23–1.35 完全兼容，不会限制环境选择。
3. **规避 alpha 变更**：`v1.16.0-alpha.*` 的调度器内部结构（如 unschedulable job cache、二级索引）仍在演进，以此为基线写的代码分析章节可能很快过时。

## 后果

- **好的后果**：
  - 所有人的数据天然可比，汇总报告的横向对比表在方法学上成立。
  - 报告里的代码引用（文件路径 + 行号）在项目周期内保持有效。
- **坏的后果 / 代价**：
  - 无法把 master 上的新特性写进报告；如果有人特别想分析新特性，需要单独提出 ADR。
  - 需要所有人重跑一次环境搭建（`scripts/setup-kind.sh` 已按此基线固定镜像 tag）。
- **需要同步更新的文件**：
  - `baseline.md`（§1、§3.2）
  - `scripts/setup-kind.sh`（镜像 tag 默认值）
  - `scripts/fetch-baseline.sh`（checkout 的 commit）

## 复审条件

出现下列任一情况时重开讨论：

1. 在 `v1.15.3` 上发现阻塞本组实验的缺陷，且该缺陷在后续版本已修复；
2. 上游发布 `v1.16.0` 正式版，且本组进度仍有余量；
3. 有组员的选题**必须**依赖 1.16 的新特性（此时应改为「主基线 v1.15.3 + 该同学单独声明例外」）。
