## 0. 一句话概括这门作业在考什么

> 不是考"你会不会 Spring/Volcano"，也不是考"你用了多少 AI"。
> 考的是：**你能不能把 AI 给的合理解释，换成有代码/测试/运行证据的、可被别人复核的项目知识。**

材料原话（结语）：
> "AI 让你更快提出'这个系统可能怎样工作'；工程证据决定'它实际上怎样工作'。"

这句话可以直接当成本项目的总纲。写报告时每写一句结论就问自己：**"我凭什么相信？"**

## 2. 五件必交成果（缺一件直接扣对应的分）

| # | 交付物 | 硬性要求 | 对应评分维度 |
| --- | --- | --- | --- |
| 1 | **一页项目地图** | 根目录、核心包、配置、测试、入口 | 项目结构分析 15 |
| 2 | **一张领域类图** | **至少 5 个核心类**，且**区分继承与关联** | 核心类与关系 15 |
| 3 | **一张业务调用链图** | 从用户动作 → 数据访问 → 返回 | 调用链分析 20 |
| 4 | **一张证据矩阵** | **至少 8 个**重要判断及其证据 | 代码证据与验证 15 |
| 5 | **一页 AI 使用反思** | ≥2 个 AI 帮助显著的地方，≥1 个**被代码纠正**的地方 | AI 使用方法 10 |

> ⚠️ 第 4 件最容易做得敷衍。8 条不是凑数，是 8 条**你原本可能会信错的判断**。
> 好的证据矩阵里，至少要有一两条的结果是"**修正**"而不是"确认" —— 全打勾的矩阵一看就是编的。

## 4. 评分量表（100 分）与"怎么拿到高分"

| 维度 | 分值 | 讲义里的高分特征 | **具体动作**（照着做） |
| --- | ---: | --- | --- |
| 项目结构分析 | 15 | 地图准确，能解释阅读顺序 | 画地图前**先不看 AI 的答案**；地图上每个区域标一个验证过的文件路径；额外用一段话说明"为什么先看这个、后看那个" |
| 核心类与关系 | 15 | 关系类型准确，有代码证据 | 每条边标注关系类型（实现/嵌入/关联/依赖/调用）**和证据位置**（文件:行号）；专门写一小节"最容易误判的一条边" |
| 调用链分析 | 20 | 端到端、顺序清楚、**包含失败路径** | 必须画**两条**链：成功路径 + 失败路径。每一步标注"框架做的 / 项目代码做的" |
| 代码证据与验证 | 15 | 重要判断可追溯 | 证据矩阵 ≥8 条，每条给 A/B/C/D 等级 + 精确位置；A 级证据（真跑过）至少 2 条 |
| 测试理解 | 10 | 能从测试反推边界 | 用 Arrange-Act-Assert 拆一个测试，写出它**定义了什么契约**；再设计 1 个**新增边界测试**（只写意图，不必写代码） |
| AI 使用方法 | 10 | 有验证、有纠错、有反思 | AI 使用日志保留原始提问 + AI 原话 + 你的核验 + 结论（确认/修正）。**至少 1 条是"修正"** |
| 图表与报告 | 15 | 结构清楚、可复用、表达专业 | 用 mermaid 源码提交（可 review、可改）；每张图有标题、图例、一句话结论；不放大段源码 |

> 加分常识：**图表与报告 15 分 + 结构 15 分 = 30 分**，接近三分之一的分靠"表达清楚"。
> 很多人把全部精力花在追代码上，最后败在图画得乱、结论没编号。别犯这个错。

## 5. AI 证据分级（贯穿全篇的核心纪律）

| 等级 | 证据来源 | 使用原则 |
| --- | --- | --- |
| **A** | 实际运行、断点、自动测试 | 优先用于确认**动态行为**（"这次真的这样发生了"） |
| **B** | 当前仓库源码与配置 | 确认**静态结构与实现细节**（"仓库里直接写明"） |
| **C** | 当前版本官方 README / 官方文档 | 确认使用方式与框架约定 |
| **D** | AI 自然语言解释 | **仅作假设，必须继续核验** |

材料里的课堂规则：
> 重要结论**至少要回到 B 级**；涉及实际行为时尽量升级到 **A 级**。

**对本组的直接含义：** 每份报告至少要真跑一次 Volcano（`scripts/setup-kind.sh` + `smoke`），
否则你的调用链只能停在 B 级，而"调用链分析"占 20 分 —— 这是最贵的一项。
而且老师答辩第 3 问会直接问："你的调用链中，哪一步是框架完成、哪一步是项目代码完成？"
没跑过的人答不上来。

## 7. 分析对象：已获教师确认 ✅

教材 §8.1 原话：

> 你将以 **Spring PetClinic** 或教师指定的**同规模**开源项目为对象，完成一份"项目理解报告"。

本组选择的是 **Volcano**（Go / Kubernetes 批调度系统）。
2026-10-05 已向教师确认，**两处偏离均获同意**：

| 偏离 | 曾经的疑虑 | 教师答复 |
| --- | --- | --- |
| **语言不同**：教材是 Java + 面向对象（继承、Service 层、Controller） | "领域类图"要求"区分**继承**与关联"，而 **Go 没有继承** | **可以** —— 用「接口实现 / 组合嵌入 / 关联 / 依赖」替代 |
| **规模不同**：Volcano 比 PetClinic 大两个数量级 | "同规模"字面上不满足 | **可以** —— 但见下方 §7.2 范围控制 |

完整记录见 [ADR-0002](adr/0002-adopt-volcano-as-subject.md)。

### 7.1 因此，§8 的映射表是**硬规范**，不是备选

画领域对象图时**必须**按 §8 标注关系类型：
接口实现 → 虚线空心三角；struct 嵌入 → 标为**组合**并显式注明"嵌入 ≠ is-a"。
把"Go 无继承"本身写成报告 §3 的一个分析点 —— 这正好是答辩第 2 问的答案。

### 7.2 范围控制（教师同意"规模可以更大"的隐含条件）

"同规模"这条虽然被豁免了，但**它的用意还在**：报告必须可读、可评。
所以每个人只对**自己认领的模块**做深度分析；项目地图与调用链覆盖全局即可，
不要试图把整个 Volcano 铺开讲 —— 那一定会变成泛泛而谈。

评审时专门检查这一条：**如果一份报告看起来像"Volcano 概述"，说明范围失控了。**

### 7.3 交付形态：教师答复"尽量"

问"报告是每人一份吗"，答复是 **"尽量"**（软要求）。
执行口径见 [ADR-0003](adr/0003-report-granularity.md)，结论是：

- **目标不变：每人一份独立报告**（5 份），各满足五件交付物；
- 允许在进度落后时降级（L1 精简 / L2 合并署名），
  但**"一条自己跑通的端到端调用链"和"一份自己的证据矩阵"不能省**；
- 理由：教材 §8.5 的 5 个答辩问题**全是第一人称**（"**你**画的类图"、"**你的**调用链"）。
  **可以合并的是文档，不能合并的是能力。**

> **还剩一个问题建议补问**（下次课上一分钟）：
> "如果个别同学只能完成部分内容，最终是每个人单独打分，还是整组一个分数？"
> 这个答案决定组长的兜底策略是按人还是按组优化。得到答复后更新 ADR-0003。

## 8. Java/OOP → Go/Volcano 概念映射表

**画类图时按这张表标注关系类型**，不要生搬 UML 的"继承"箭头。

| 教材里的概念（Java） | Volcano 里的对应物 | 怎么画 / 怎么写 | 常见误判 |
| --- | --- | --- | --- |
| 类 `class` | 结构体 `struct` | 方框 | — |
| 接口 `interface` | 接口 `interface` | 方框 + `«interface»` | — |
| 继承 `extends` | **没有直接对应物** | 不要画继承箭头 | 把 struct 嵌入当成继承 —— **这是最容易被老师抓的点** |
| 嵌入 `embedding`（Go 特有） | 组合 + 方法提升 | 画**组合**（实心菱形/普通关联），图注写明"嵌入提供方法提升但不构成 is-a" | 说成"Go 的继承" |
| 实现 `implements` | 隐式接口实现 | **虚线空心三角**，箭头指向接口 | Go 是隐式实现，代码里搜不到 `implements`，要给出"哪个方法集满足了哪个接口"的证据 |
| 字段持有 `has-a` | struct 字段 | 关联箭头，标字段名 | — |
| 构造器注入依赖 | 函数参数 / 结构体字段注入 | 依赖虚线箭头 | 与关联混淆 |
| 方法调用 | 普通函数调用 | **不画在类图上**，画在调用链图上 | 所有箭头都写"调用" —— 教材明确点名的学生误区 |
| `Controller` | `cmd/*/main.go` + `pkg/webhooks/admission/*` | — | — |
| `Service` 层 | 各 `pkg/*` 包内的业务函数 | — | 别硬套三层架构（教材 §2.4 专门警告"架构幻觉"） |
| `Repository` / JPA | `client-go` clientset / informer 本地缓存 `pkg/scheduler/cache` | — | 注意 Volcano 大量读**本地缓存**而不是直连 API Server |
| `main()` 启动 | `cmd/scheduler/main.go` → `pkg/scheduler/scheduler.go` | 启动链图 | — |
| Web 请求入口 | `kubectl apply vcjob` → admission webhook → controller → scheduler | 调用链入口 | 说"Volcano 没有 Web 入口"就等于放弃 20 分；改用 CLI/API 动作作为入口 |
| 数据库 | etcd 中的 CRD 对象（Job / PodGroup / Queue） | "数据访问"环节 | — |

**推荐的 Volcano 端到端调用链（20 分那一项）—— 对应"新增 Owner"：**

```
用户动作：kubectl apply -f vcjob.yaml（提交一个 Volcano 作业）
  → ① kube-apiserver 接收，写入 etcd（框架）
  → ② volcano-admission webhook 校验（项目代码，pkg/webhooks/admission/jobs）
  → ③ volcano-controllers 的 Job Controller 创建 PodGroup 与 Pod（项目代码，pkg/controllers）
  → ④ volcano-scheduler 感知 PodGroup，进入调度周期（项目代码，pkg/scheduler）
  → ⑤ enqueue → allocate 两个 Action 依次执行（项目代码）
  → ⑥ gang / proportion / predicates 等插件参与决策（项目代码）
  → ⑦ 决策写回 Pod.spec.nodeName（项目代码），kubelet 拉起容器（框架）
  → 返回：kubectl get pods 看到 Running
```

**失败路径**（必须有，占分）：`minAvailable` 不满足时 PodGroup 保持 `Inqueue/Pending`，
allocate 放弃整组，Pod 停留 Pending —— 这条链要单独画并给出证据。

## 9. 组内必须守住的三条对齐纪律

1. **基线一致**：所有人跑同一版本（[baseline.md](../baseline.md)），否则第 3 节里的行号和结论对不上。
2. **证据分级一致**：所有人都用 A/B/C/D 四级，别自创标准。
3. **图各自画**：项目地图 / 类图 / 调用链图**必须自己画一遍**（可以互相讨论），
   因为评分和答辩考的是"你从哪里知道"，抄来的图你答不上第 2、3 问。
   报告里**允许**出现相似甚至相同的图 —— 大家分析的是同一个项目，这是正常的。
